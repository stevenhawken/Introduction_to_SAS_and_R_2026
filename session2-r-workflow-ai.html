The question we’re answering

Using a synthetic linked birth cohort: is 17-hydroxyprogesterone (17-OHP) measured on the newborn screening dried blood spot associated with gestational age — and do maternal factors predict preterm birth?

Three files, exactly the shape of a real linked extract:

File Unit Key n
births.csv one row per infant infant_id, momid 1,239
mothers.csv one row per mother momid 1,200
screening.csv one row per specimen infant_id + specimen_no 1,338

1,239 infants but only 1,200 mothers, and 1,338 specimens for 1,239 infants. Those two mismatches are the whole lesson of the joins section. Fully synthetic data — safe to share, safe to paste anywhere.

The workflow

Every analysis is the same six steps

1 · Import → get it into R, as the right types
2 · Tidy → one row per observation, one column per variable
3 · Transform → filter, derive, join, aggregate
4 · Visualise → look at it before you model it
5 · Model → the part that takes 5% of the time
6 · Communicate → tables, figures, a reproducible document

Steps 1–3 are 80% of the work and where essentially all the errors live. A wrong left_join() will not throw an error — it will quietly give you a different cohort. That is why today is mostly steps 1–3.

haven::read_sas() is the bridge. Your supervisor’s .sas7bdat opens in R without SAS installed, formats and labels included. This is how most people move from SAS to R.

read_csv() guesses column types from the first 1000 rows. If a numeric column has "N/A" at row 4000, you get a character column. Always check spec() or glimpse().

The pipe: |>

The pipe takes the thing on the left and makes it the first argument of the thing on the right. It turns nested code inside-out so you read it in the order it happens.

Without

arrange(
  filter(
    select(births, infant_id, ga_weeks, site),
    ga_weeks < 37),
  ga_weeks)

Read from the inside out. Nobody enjoys this.

With

births |>
  select(infant_id, ga_weeks, site) |>
  filter(ga_weeks < 37) |>
  arrange(ga_weeks)

“Take births, then select, then filter, then sort.”

Ctrl/Cmd + Shift + M inserts a pipe in RStudio. You’ll also see %>% from magrittr in older code — they behave the same for our purposes.

Verb 1–2: filter() and select()

filter() picks rows. select() picks columns.

R 

filter(ga_weeks < 37)
select(id, ga_weeks)

SAS 

IF ga_weeks < 37;
KEEP id ga_weeks;

Verb 3: mutate() — deriving variables

case_when() evaluates top to bottom and stops at the first match — exactly like a SAS IF/ELSE IF chain. Order your conditions from most specific to least.

Your turn: derive and categorise

Create a birth-weight category and count it.

Hint

The conventional low-birth-weight cut-point is 2500 g. To tabulate a variable in dplyr, the verb is count().

Solution

births |> mutate( bw_cat = case_when( birth_weight_g < 1500 ~ "very low", birth_weight_g < 2500 ~ "low", .default = "normal" ) ) |> count(bw_cat) 
births |>
  mutate(
    bw_cat = case_when(
      birth_weight_g < 1500 ~ "very low",
      birth_weight_g < 2500 ~ "low",
      .default = "normal"
    )
  ) |>
  count(bw_cat)

Verbs 4–5: group_by() + summarise()

This pair replaces PROC MEANS / PROC SUMMARY and does far more.

.groups = "drop" un-groups the result. Forget it and every later verb silently operates within group — a subtle and very common bug.

Your turn: group and summarise

Mean and SD of gestational age, by delivery mode, with the number in each group.

Hint

The grouping verb is group_by(). n() counts rows in the current group (no arguments). sd() is the standard deviation.

Solution

births |> group_by(delivery_mode) |> summarise( n = n(), mean_ga = mean(ga_weeks), sd_ga = sd(ga_weeks), .groups = "drop" ) 
births |>
  group_by(delivery_mode) |>
  summarise(
    n       = n(),
    mean_ga = mean(ga_weeks),
    sd_ga   = sd(ga_weeks),
    .groups = "drop"
  )

Joins

The four joins you need

left_join(a, b, by = "id")

Keep all of a. Unmatched rows of a get NA. This is your default. It preserves your cohort. 

inner_join(a, b, by = "id")

Keep only rows present in both. Silently drops cases — so always know how many. 

full_join(a, b, by = "id")

Keep everything from both. Useful when assembling a cohort from multiple registries. 

anti_join(a, b, by = "id")

Rows of a with no match in b. An auditing tool — “who is missing a screening result, and are they different?”

R 

left_join(births, mothers, by = "momid")

SAS 

DATA out; MERGE births(IN=a) mothers;
  BY momid; IF a; RUN;

The join that ruins analyses live

Your cohort just grew by 133 rows. 133 infants had a repeat screening specimen, so each of them now contributes two rows. Every subsequent n(), mean, and regression is now weighted towards infants who were screened twice — which is to say, towards the sickest infants. Nothing errored. Nothing warned you.

Fix it: decide which record you want

The habit that will save you: print nrow() before and after every join. If the number changed and you didn’t expect it to, stop.

anti_join() — who did we lose, and are they different?

If the unmatched infants are systematically smaller or earlier, your complete-case analysis is biased and you need to say so. This three-line check belongs in every linkage paper you write.

One more trap: many-to-one on the mother

That is not a bug — an infant-level analysis correctly has one row per infant. But those infants are not independent, so a standard glm() understates the standard errors. You would need a cluster-robust variance or a random effect for momid. Recognising the clustering is the epidemiology; the join is just plumbing.

Your turn: build the analysis cohort

Hint

You want only the first specimen, so specimen_no should equal 1 (==). For the second join you want to keep every infant, so use left_join().

Solution

analysis <- births |> mutate(sex = toupper(sex)) |> left_join(screening |> filter(specimen_no == 1), by = "infant_id") |> left_join(mothers, by = "momid") nrow(analysis) nrow(analysis) == nrow(births) 
analysis <- births |>
  mutate(sex = toupper(sex)) |>
  left_join(screening |> filter(specimen_no == 1), by = "infant_id") |>
  left_join(mothers, by = "momid")

nrow(analysis)
nrow(analysis) == nrow(births)

Dates, missingness, shape

Dates with lubridate

read_csv() parses ISO-style datetimes for you; read.csv() leaves them as text. When a date arrives as text — and from SAS or Excel it usually does — parse it explicitly with the function whose name is the format: ymd(), dmy(), ymd_hm(), mdy_hms().

Date arithmetic: time to specimen collection

R 

as_date(x); year(x); month(x, label = TRUE)
difftime(b, a, units = "hours")

SAS 

dob = DATEPART(birth_dtm);
FORMAT dob date9.;
hrs = INTCK('hour', birth_dtm, coll_dtm);

Missing data — think, then act

drop_na() is one keystroke and a substantive decision. Complete-case analysis is only unbiased under MCAR — a strong assumption you should state and, ideally, test. For anything going in a paper, look at mice for multiple imputation.

Wide → long with pivot_longer()

Five analytes in five columns is convenient for storage and useless for plotting.

pivot_wider() goes the other way. In SAS this is PROC TRANSPOSE, which is — and this is a defensible professional opinion — considerably less pleasant.

A publishable “Table 1”

In RStudio, gtsummary::tbl_summary(data, by = preterm) |> add_p() does all of this — with formatting, p-values, and export to Word — in two lines. Try it locally: install.packages("gtsummary").

Modelling

Linear and logistic, and broom

broom::tidy() turns any model into a data frame — so odds ratios and CIs flow straight into ggplot(), knitr::kable(), or a .csv for your manuscript. No more copying numbers out of printed output by hand. That alone is worth the switch from SAS.

Checking the model, and the R ↔︎ SAS map

glance(m1)          # R², AIC, F, df
augment(m1)         # fitted values + residuals
par(mfrow = c(2,2)); plot(m1)

augment() gives you residuals as a column, so diagnostics are just another ggplot.

AI coding assistants

What we’re talking about 15 min

Examples Where it lives
Chat assistants Claude, ChatGPT, Gemini Browser. You paste code in and out.
In-editor completion GitHub Copilot, Positron Assistant, RStudio + chattr/ellmer Suggests as you type, sees your open files
Agentic tools Claude Code, Codex, Cursor Reads and writes files, runs code, iterates
Institution-hosted Azure OpenAI / Bedrock behind a hospital firewall Same models, data stays inside the tenancy

These are now ordinary tools for research programming, and pretending otherwise does not serve you. But they are assistants, not analysts — the last two rows of this table are also where the data-governance questions get serious.

What they are genuinely good at

  • Translating between languages. “Here is a SAS PROC LOGISTIC with a CLASS statement — write the R equivalent.” This works remarkably well and is worth knowing about on day one.
  • Boilerplate and syntax you’d otherwise look up. ggplot theming, regex, reshaping, date parsing, case_when chains.
  • Explaining code you inherited. “What does this 200-line DATA step actually do?” — then you verify.
  • Decoding error messages. Paste the error and the offending line; you’ll usually get a real answer faster than a search.
  • Writing comments and documentation for code you already wrote and understand.
  • Being a rubber duck at 11pm when your supervisor is asleep.

The hard rules for health data

Nothing that identifies a person, and nothing from a secure analytic environment, ever goes into a cloud AI tool. No exceptions, no “just this once”, no “it’s only 10 rows”.

  • No row-level data. Not ICES, not BORN, not TOHDW, not your REB-approved chart abstraction. Pasting it is a privacy breach and likely a DUA violation, whether or not anything bad happens next.
  • Secure environments are secure environments. If you cannot copy data out, you cannot copy data out into a chat window either. That includes screenshots.
  • Direct identifiers are obvious; indirect ones are not. Postal code + birth date + rare diagnosis re-identifies a person as surely as a name.
  • Your DUA and REB protocol govern. Read the data-sharing clause. Ask your data custodian before, not after.
  • Check your institution’s policy. uOttawa, OHRI, CHEO and ICES each have one, and they differ.

How to work safely anyway

Send the schema, never the data

# paste THIS, not the dataset
str(analysis)
# or an obviously fake sample:
head(analysis) |>
  mutate(across(everything(),
                ~ sample(.x)))

The model needs column names and types to write correct code. It does not need your patients.

Develop on synthetic data

Write and debug against simulated data that has the same structure (exactly like the files we used today), then move the finished script into the secure environment and run it there. This is how a lot of professional analytic work is actually done, and it is a defensible workflow to describe in a methods section.

Ask about an institution-hosted option. Many hospitals and universities now run models inside their own tenancy where data does not leave the boundary. That changes the calculus — but confirm it in writing, don’t assume it from a vendor’s marketing page.

Prompting for code you can actually use

Weak

make me a graph of birth weight

Strong

I have a data frame `analysis` (1239 rows):
ga_weeks (num), birth_weight_g (int),
sex (chr "M"/"F"), site (chr, 5 levels).

Write tidyverse/ggplot2 code for a scatter
plot of birth weight vs gestational age,
faceted by sex, with a linear smooth and
95% CI. Label axes for a journal figure.
Comment each step. R 4.4, ggplot2 3.5.
  • State the dialect — “tidyverse”, “base R”, “data.table”. Otherwise you get a mash of all three.
  • Give the schema and the row count. Column names and types are what it actually needs.
  • Ask for comments, then read them. If a comment doesn’t match the code, the code is wrong.
  • Ask it to explain its choice of test/model. A vague justification is a red flag.
  • Iterate. “That dropped the NAs silently — rewrite it so missingness is explicit.”

The hallucination trap

These models are trained to produce plausible text. Plausible R code that runs and returns a number is the most dangerous possible failure mode, because nothing alerts you.

  • Invented functions and arguments. tidyverse::clean_names(), geom_boxplot(se = TRUE), a conf.level argument that doesn’t exist. These at least error.
  • Wrong defaults, silently. mean() without na.rm. cor() dropping pairs. type = "response" omitted from predict().
  • Statistically wrong but syntactically perfect. A gaussian family on a binary outcome. A t-test on paired data. Ignoring clustering by mother. It runs. It prints. It’s wrong.
  • Confidently wrong citations and package claims. It will tell you a package does something it does not.
  • Sycophancy. Push back on a correct answer and it will often “correct” itself into an error.

You are the author. Your name goes on the paper; the model’s does not. Treat generated code exactly as you would code from a fast, confident, well-read summer student who has never once said “I’m not sure”.

Live exercise: spot the bugs 8 min

I asked an assistant for “the analysis of preterm birth”. It produced this. It runs. There are four things wrong with it. Find them, then fix them.

Hint

  1. Compare nrow(cohort) with nrow(births). Which join changed the row count, and why?
  2. Look at mean_17ohp. Why is it NA?
  3. Look at the output of count(cohort, sex). How many sexes are there?
  4. ga_weeks < 37 is TRUE/FALSE. Is gaussian the right family for that — and does exponentiate = TRUE mean anything if it isn’t?

Solution

# 1. Keep ONE screening record per infant, or the cohort inflates 1239 -> 1372 # 2. mean() needs na.rm = TRUE; 17-OHP has missing values # 3. sex is coded F/M/f/m and must be harmonised before it is used # 4. A binary outcome needs family = binomial; only then does exponentiate = TRUE # give odds ratios rather than nonsense cohort <- births |> mutate(sex = toupper(sex)) |> left_join(filter(screening, specimen_no == 1), by = "infant_id") |> left_join(mothers, by = "momid") stopifnot(nrow(cohort) == nrow(births)) # guard rail: fail loudly cohort |> summarise( n = n(), mean_bw = mean(birth_weight_g, na.rm = TRUE), mean_17ohp = mean(x17ohp, na.rm = TRUE), n_missing_17ohp = sum(is.na(x17ohp)) ) count(cohort, sex) m <- glm(I(ga_weeks < 37) ~ mat_age + smoking + mat_bmi, data = cohort, family = binomial) tidy(m, exponentiate = TRUE, conf.int = TRUE) # (and note: twins mean rows are clustered within momid — a robust or # mixed-effects variance would be more honest still)

A workable policy for your thesis

  1. Never paste real data, output containing small cells, or anything from a secure environment.
  2. Use it freely for syntax, translation, explanation, and debugging.
  3. Run every line yourself and check the intermediate objects — nrow(), count(), summary().
  4. Never accept a statistical choice you couldn’t defend in your comprehensive exam.
  5. Keep the code in version control so you can see what changed and when.
  6. Disclose it if your journal, funder, or program asks — and increasingly they do.

The skill that matters is no longer typing ggplot from memory. It is knowing when the answer is wrong — and that still comes from understanding your data and your methods. That is what this degree is for.
